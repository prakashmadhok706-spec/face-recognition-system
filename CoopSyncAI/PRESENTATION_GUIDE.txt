PART 6: SYSTEM ARCHITECTURE EXPLAINED FOR JURY INQUISITION
================================================================================

If a technical judge asks you to walk through the architecture:

1. Request Pipeline:
   Browser HTML5 Canvas -> Base64 JPEG -> FastAPI Router -> `face_engine.py` / `qr_engine.py`
   -> Haversine GPS Validator -> SQLAlchemy 2.0 ORM -> SQLite (`coopsync.db`) -> JSON Response.

2. Face Engine Architecture:
   - Detection: `cv2.CascadeClassifier('haarcascade_frontalface_default.xml')`
   - Preprocessing: `cv2.cvtColor(BGR2GRAY)` + `cv2.resize(200, 200)` + `cv2.equalizeHist()`
   - Anti-Spoof: `cv2.Laplacian(face_roi, cv2.CV_64F).var() > 45.0`
   - Classification: `cv2.face.LBPHFaceRecognizer.predict(face_roi)`
   - Thresholding: Confidence >= 65.0% (Distance <= 76.0). Formula: `100 - (dist * 0.46)`.

3. Dynamic QR Architecture:
   - Secret Salt + UUIDv4 Session ID + Unix Expiry Timestamp.
   - SHA-256 Hash Digest: `hashlib.sha256(f"{id}|{name}|{exp}|{SALT}".encode()).hexdigest()[:16]`
   - Session Tracking: Thread-safe in-memory set preventing duplicate scans per student ID.

4. Geofencing Engine:
   - Mathematical model: Haversine Great-Circle metric ($R = 6,371,000\text{m}$).
   - Authoritative backend validation guarding against missing coordinates, NaN/Inf,
     accuracy degradation ($>100\text{m}$), and out-of-perimeter location ($>50\text{m}$).

PROFILE 1: THE COMPUTER VISION / AI SPECIALIST
--------------------------------------------------------------------------------

Q1: "Why did you use LBPH instead of a modern deep learning model like ArcFace or FaceNet?"
A: "Respected Judge, engineering is about optimizing for real operational constraints.
    Problem Statement SIH26087 targets rural cooperative training centers equipped with
    basic Dual-Core PCs. FaceNet and ArcFace require dedicated GPUs, 500MB+ memory footprint,
    and 200ms+ CPU latency. LBPH executes in under 5 milliseconds on CPU, requires zero GPU,
    trains on 50 samples in ~1 second, and produces a lightweight 15MB model file.
    Furthermore, our modular `FaceRecognitionEngine` class allows tier-1 institutions with
    GPU clusters to swap in deep vector embeddings without altering our REST APIs."

Q2: "Laplacian variance can be fooled by a high-resolution 4K tablet display. How do you defend against that?"
A: "A high-resolution screen still has physical glass that causes specular glare and
    reflections under ambient light, which distorts micro-texture variance below 45.
    More importantly, CoopSync AI employs defense-in-depth:
    1. The student must also be physically inside the 50-meter GPS campus perimeter.
    2. Instructors can enforce Dynamic QR mode where the rotating token expires in 30 seconds.
    3. Our architecture is designed to integrate Eye Aspect Ratio (EAR) blink detection
       and random head-pose challenge-response as future firmware upgrades."

Q3: "How does LBPH handle changes in facial hair, glasses, or aging?"
A: "LBPH partitions the face into an 8x8 spatial grid of 64 independent local histograms.
    If a student wears glasses or grows a beard, only the histograms for the eye or chin
    cells change; the remaining forehead, nose, and cheek histograms remain consistent.
    Furthermore, our web-based enrollment tool allows students to update their 50-frame
    profile in 6 seconds whenever their appearance changes."

PROFILE 2: THE CYBERSECURITY & NETWORKING SPECIALIST
--------------------------------------------------------------------------------

Q4: "Can a student spoof their GPS using a Fake GPS Android application?"
A: "Fake GPS apps typically report synthetic 0.0m accuracy or abrupt teleportation jumps.
    CoopSync AI enforces:
    1. Maximum accuracy bounds: Any signal worse than ±100m or suspiciously perfect is flagged.
    2. Dual-Factor Coupling: A fake GPS alone does nothing because attendance still requires
       the student's physical face to pass live biometric recognition.
    3. In enterprise deployments, the system cross-references device IP subnets and Wi-Fi
       BSSID access points."

Q5: "How do you prevent a replay attack where a student intercepts the network request?"
A: "Every attendance submission requires a unique cryptographic signature. In QR mode,
    the session expires in 30 seconds and tracks student IDs in a thread-safe `used_by` set.
    Once an ID is recorded for that session, any replayed request returns HTTP 400:
    'You have already scanned this session'. Additionally, daily database bounds prevent
    multiple check-ins on the same calendar day."

Q6: "How do you prevent SQL injection and cross-site scripting (XSS)?"
A: "1. We use SQLAlchemy 2.0 ORM with parameterized prepared statements, preventing SQL injection.
    2. FastAPI leverages Pydantic v2 schemas that enforce strict type validation on all inputs.
    3. React automatically escapes JSX text expressions, preventing stored and reflected XSS."

Q10: "Why SQLite instead of PostgreSQL?"
A: "SQLite was chosen for local development, rapid evaluation, and standalone edge offline

    `DATABASE_URL=postgresql://user:pass@host:5432/coopsync`. Zero application code changes

    5. Orchestration: Kubernetes with Horizontal Pod Autoscaling based on request traffic."
